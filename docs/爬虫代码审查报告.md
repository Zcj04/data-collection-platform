## 一、美团 — 已审查

### 1.1 代码组成

美团由**两份独立脚本**串联完成完整流程：

| 脚本 | 职责 | 主函数签名 | 输入 | 输出 |
|---|---|---|---|---|
| 脚本1（下载+解析） | 从美团商户后台下载 Excel 报告并解析为店铺维度数据 | `main(begin_date, end_date)` | 起止日期字符串 `YYYY-MM-DD` | `List[Dict]`：每店铺一条 |
| 脚本2（场地匹配） | 把店铺维度数据按数据库映射到"场地"维度 | `main(meituan_data)` | 脚本1 的输出 | `List[Dict]`：每场地一条 |

### 1.2 脚本1 详细审查

**函数清单**：
- `get_shop_id_list(MTGSIG, COOKIE, COMMON_PARAMS)` — 获取店铺 ID 列表
- `request_download(begin_date, end_date, MTGSIG, COOKIE, BASE_URL, COMMON_PARAMS, shopIdList)` — 提交下载请求
- `get_latest_download_id(begin_date, MTGSIG, COOKIE, BASE_URL, COMMON_PARAMS)` — 获取最新下载任务 ID
- `get_file_url(download_id, MTGSIG, COOKIE, BASE_URL, COMMON_PARAMS)` — 轮询下载链接
- `download_excel(file_url, filename)` — 下载 Excel 文件
- `get_dict_list(file_name)` — 解析 Excel，分组求和
- `search_file_by_keyword(folder_path, keyword)` — 按关键字查找已下载文件（缓存复用）
- `main(begin_date, end_date)` — 主入口

**主入口 `main(begin_date, end_date)` 返回结构**：
```python
[
  {"美团店铺名": "xxx店", "美团收款": 12345.67, "美团实收": 11000.00, "美团手续费": 1345.67},
  ...
]
```

**业务流程**（已封装完整）：
```
获取店铺ID → 提交下载请求 → 获取下载任务ID → 轮询下载链接 → 下载Excel
   → 解析Excel(skiprows=1) → 清洗"账户名称"得"美团店铺名"
   → 按店铺分组求和[总收入（元）、结算价（元）] → 计算手续费 → 返回字典列表
```

**依赖**：`requests`、`pandas`、`openpyxl`、标准库（json/time/datetime/warnings/os）

### 1.3 脚本2 详细审查

**主入口 `main(meituan_data)` 返回结构**：
```python
[
  {"场地": "深C广场", "美团收款": 12345.67, "美团实收": 11000.00, "美团手续费": 1345.67},
  ...
]
```

**业务逻辑**：
- 连接 MySQL（`store_mapping_db` 库，`company_organizational_structure` 表）
- 查询 `venue` 与 `meituan_sjxg` / `meituan_sjxg1234` 建立映射 `{美团店铺名: 场地名}`
- 美团数据按店铺名匹配到场地，复制数值字段
- 数据库有但美团没有的场地 → 数值填 0
- 美团有但数据库没匹配的店铺 → 打印警告

**依赖**：`pymysql` + 在线 MySQL 数据库（localhost:3306）

### 1.4 ⚠️ 关键发现：mtgsig 现状

**mtgsig 是硬编码的，不是动态生成的。**

脚本1 的 `main` 函数内有一个 `MTGSIGS` 列表，含两个写死的 mtgsig 字符串（URL 编码的 JSON，含 `a2` 时间戳字段如 `1784779879450`）。同样 `COOKIES` 和 `partners_id` 也是硬编码的两个账号。

**影响**：
- mtgsig 含时间戳，**会随时间失效**（美团风控会拒绝过期签名）
- 当前每次运行依赖这两个硬编码签名有效；失效后需手动从浏览器抓包替换
- 这不是真正的"动态签名生成"，而是"抓包复制"——这正是用户"爬虫不是很好"的体现

**对方案的决策**：
- ❌ 不在本次项目内做 mtgsig 动态逆向（工程量大、易被反制、合规风险高）
- ✅ 把 mtgsig + Cookie 当作**凭证**纳入凭证管理页，用户定期手动更新（从浏览器 DevTools 抓包粘贴）
- ✅ 适配器检测到签名失效（请求返回异常）时，标记 failed 并提示用户更新凭证
- ⏳ 过渡方案：阶段2 先按原样集成（凭证硬编码在脚本1内，用户更新时编辑代码）；阶段4 再做凭证外置化

### 1.8 适配器集成方案（回填技术文档）

美团适配器串联两份脚本：

```python
# adapters/meituan_adapter.py 伪代码
import importlib
from adapters.base import CrawlerAdapter
from core.models import CrawlerResult, Metric

class MeituanAdapter(CrawlerAdapter):
    PLATFORM = "meituan"

    def run(self, date: str) -> CrawlerResult:
        # 脚本1：下载+解析（date 同时作为 begin/end）
        dl = importlib.import_module("crawlers.meituan_download")
        shop_data = dl.main(date, date)           # → 店铺维度 List[Dict]

        # 脚本2：场地匹配
        mt = importlib.import_module("crawlers.meituan_match")
        venue_data = mt.main(shop_data)           # → 场地维度 List[Dict]

        # 标准化为 List[Metric]（按场地聚合或按场地展开，待确认维度）
        metrics = self._normalize(venue_data)
        return CrawlerResult(platform=self.PLATFORM, date=date, metrics=metrics)
```

**分步进度更新**：脚本1 内部是异步多步骤，但原脚本未暴露进度回调。过渡方案：适配器按"调用脚本1→调用脚本2"两大步更新进度（25%/75%/100%），精细分步需后续轻改脚本1 暴露钩子。

## 三、抖音（平台3）— 已审查

### 3.1 代码组成

两脚本串联：`douyin_fetch.py`（Playwright登录+API拉数据）+ `douyin_match.py`（MySQL场地匹配）

### 3.2 流程

```
本地Cookie → 失效?Playwright打开浏览器自动登录(headless=False)
   → 填手机号密码+勾协议+点登录 → 遇风控抛LoginBlocked → 保存Cookie
   → API拉收入分类(分页,2个ROOT_LIFE_ACCOUNT_IDS) → 合并 → douyin_4630/douyin_2358匹配场地
```

### 3.3 凭证

| 凭证 | 状态 | 处理 |
|---|---|---|
| 账号密码 | 已支持环境变量(`DOUYIN_LIFE_ACCOUNT/PASSWORD`)，默认值在代码里 | 适配器从凭证管理设环境变量 |
| Cookie | 本地缓存4文件 | 自动复用，失效自动Playwright重登 |

### 3.4 风险

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| 1 | Playwright headless=False | 高 | 登录时浏览器窗口弹出，可能打扰用户 |
