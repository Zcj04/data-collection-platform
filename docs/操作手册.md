# 数据采集平台 — 操作手册

> 面向数据专员，日常使用指南

## 1. 启动

打开终端（命令提示符），进入项目目录后运行：

```
python app_fastapi.py
```

浏览器访问：

- 首次初始化：`http://localhost:8010/setup`（仅本机、仅尚未创建用户时可用）
- 登录：`http://localhost:8010/login`
- 数据门户：`http://localhost:8010/portal`（根路径 `/` 也会打开门户）
- 管理后台：`http://localhost:8010/admin`

首次启动后，打开 `/setup` 创建第一个超级管理员。系统不会生成默认账号或默认密码；创建成功后初始化入口自动关闭。以后统一从 `/login` 登录，系统会按账号权限进入数据门户或管理后台。

正式服务由 Windows 用户级任务计划 `WorkBuddy-Data-Collection-8010` 守护，用户登录后自动启动；应用异常退出后启动器等待 15 秒重启，启动器自身退出时任务计划等待 1 分钟重试。当前服务仍只监听 `127.0.0.1`，仅本机可以连接。

受控停止服务时使用 `& .\scripts\stop_fastapi_service.ps1`，不要只执行 `Stop-ScheduledTask`；Windows 可能保留任务启动的 Python 子进程。

正式采集使用独立 worker 进程运行各平台；平台超时或停止请求会回收对应 worker，避免单个平台卡住整批采集。

> 推荐使用项目自带 Python 3.13 环境：
> `C:\Users\youruser\.workbuddy\binaries\python\envs\default\Scripts\python.exe app_fastapi.py`

> 说明：Streamlit 版本已停用并从当前仓库移除，日常使用请以网页版工作台（8010）为准。

## 2. 账号与权限

### 2.1 权限说明

| 权限 | 能力 | 自动包含 |
|------|------|----------|
| `portal.view` | 登录并查看企业数据门户 | — |
| `portal.download` | 下载门户汇总 Excel | `portal.view` |
| `boss_report.download` | 下载每月货款比老板报表 | `portal.view` |
| `monitoring.view` | 查看数据监控和质量检查结果 | — |
| `payment.view` | 查看每日货款和货款核算数据 | — |
| `payment.manage` | 上传、修订和执行货款相关操作 | `payment.view` |
| `admin.access` | 进入管理后台并覆盖已拆分的业务模块权限 | `portal.view` |
| `users.manage` | 创建、启停用户，修改权限并重置他人密码 | `admin.access`、`portal.view` |

财务、老板等可授予 `portal.view`、`portal.download`、`boss_report.download`、`monitoring.view` 和 `payment.view`，但不应授予 `admin.access`。货款管理员使用 `payment.manage`；只有负责平台维护的人员才应授予 `admin.access`，用户管理权限应限制在少数管理员账号。

### 2.2 创建和维护账号

拥有 `users.manage` 权限的管理员可在 `/admin` 左侧打开 **用户管理**：

1. 填写登录账号、姓名和密码。
2. 勾选所需权限并创建账号。
3. 在用户列表中启用或停用账号、调整权限。
4. 忘记密码时可为其他用户重置密码；不能在此处重置当前登录账号的密码。

系统会阻止停用当前账号、移除当前账号的后台/用户管理权限，以及移除最后一个有效用户管理员。用户被停用、权限被修改或密码被重置后，其现有登录会话会立即失效。

### 2.3 登录安全

- 登录状态保存在 HttpOnly Cookie 中，服务端只在 SQLite 保存随机会话令牌的哈希。
- 登录会话有效期为 12 小时，到期后需重新登录。
- 所有已登录的写请求都需要 CSRF 校验；正常使用网页时由前端自动携带，无需手工操作。
- 使用完毕可点击侧边栏账号区域的退出按钮，立即注销当前会话。

## 3. 日常采集流程

以下采集与维护操作均在管理后台 `http://localhost:8010/admin` 完成。

### 3.1 首次使用：填写凭证

1. 点击左侧 **凭证管理**
2. 在平台卡片（如芸苔）中填写账号密码
3. 点击 **保存**，提示"凭证已加密保存"即成功
4. 重复以上步骤填写所有平台

> 美团、抖音等平台的 Cookie/签名仍可能过期；自动采集出现部分成功时，先在凭证管理和采集日志中检查对应平台。

### 3.2 经营数据自动采集

系统启动后默认开启经营数据自动排程，使用 `Asia/Shanghai` 业务时间：

- 每日 **10:10** 采集目标月份 **1 日至昨日** 的正式累计数据。例如 8 月 25 日执行范围为 8 月 1 日至 8 月 24 日；当天未安排采集，避免把未结束的当日数据当成正式数据。
- 如服务在预定时间未运行，当日重新启动后会检查并补跑已错过的时段。
- 管理后台显示最近自动采集结果、月累计范围、13 个数据源的覆盖情况、真实入库时间和下次运行时间。
- 最近批次为 `partial`、`failed` 或 `expired` 且尚未恢复时，自动采集卡会出现“自动采集有待处理项”；点击 **查看并补采** 会带入目标日期并跳转到采集日志的数据健康检查。
- 数据门户也显示当前日期的真实入库时间、数据源覆盖和下次排程；这些状态不代表所有数源一定成功。

自动排程与“会员资产监控”的 10:00/10:30–19:00 同步是两套独立任务：前者写入经营汇总，后者只处理多金宝会员资产事件。

> 普通 `portal.view` 用户只能看数据，不能触发采集。请不要为了“随时拉取”给查看人员授予 `admin.access`。

失败和部分失败事件会先写入本地 `alert_events`，避免服务重启后丢失。若在 `.env` 配置 `WORKBUDDY_ALERT_WEBHOOK_URL`，服务会异步投递到该 HTTPS 地址并重试；留空时只保留本地事件。告警不会直接启动重跑，仍需管理员查看日志页健康结果后决定补采。

### 3.3 管理员手动采集与补采

1. 点击左侧 **数据看板**
2. 选择日期
3. 点击 **全部采集**，系统自动并行抓取所选日期范围
4. 在侧边栏平台状态和「最近日志」中查看实时进度
5. 完成后汇总报表自动展示数据

自动批次为 `partial`、`failed`、`expired`，或临时需要其他日期时，由管理员使用“全部采集”、单平台重跑或采集日志中的“补采缺失/失败平台”兜底。

### 3.4 导出

- 数据看板底部点击 **📥 导出Excel**
- 生成带日期的 `.xlsx` 文件

### 3.5 单平台重试

- 侧边栏平台状态中看到 ❌ 失败平台
- 鼠标悬停该平台，点击 ▶ 按钮单独重跑该平台

点击停止后，页面先显示“停止中”。Python 线程不能安全强杀正在进行的第三方请求；当前平台调用释放后才显示“已停止”，迟到结果不会入库。任务超时同理先显示“超时清理中”，清理期间不会启动重叠批次。

### 3.6 数据大屏

- 左侧 **数据大屏**：选择日期后点击「检查数据」，查看月度经营仪表盘（总收入 / 完成率 / 内地与香港 TOP3 / 单日 TOP3 / 门店完成度 / 区域完成度）

> 门店完成度：目标来自每月目标表（`data/targets/`），颜色表示完成情况（绿≥100% / 黄70-99% / 红<70%）；区域完成度需先配置门店-区域对照。

### 3.7 每日经营数据

- 左侧 **每日经营数据**：选择经营日期和门店，查看单日总收入及各平台收入
- 普通日期按「截止日累计 − 前一自然日累计」计算；每月1日直接使用当日累计
- 页面会区分数据完整、部分缺失、累计快照缺失和历史口径未验证；缺失数据不会按0计算
- 有收入的平台才展示；缺失平台会在状态提示中列出，管理员可前往采集日志的数据健康检查处理
- 对某个平台金额有疑问时，点击金额旁的 **追查**，系统会在新标签页打开该源平台；也可以使用门户顶部或后台侧边栏的 **源平台入口** 查看全部来源
- 平台入口不会自动传递采集账号、密码或 Cookie，仍需在源平台按其自身方式登录；精简、八达通、货款属于 API 或本地文件来源，因此显示 **无入口**

### 3.8 采集日志与数据健康

日志页同时查看任务执行记录和当日数据是否健康。

1. 点击左侧 **采集日志**，选择日期后自动加载日志和健康检查
2. 查看平台是否入库、最新任务状态、门店覆盖数与待处理问题；即使已有旧数据，最新任务为 `failed` / `stopped` 时也会提示“当前展示的可能是旧数据”
3. 存在缺失或最新失败/停止的平台时，可点击 **补采缺失/失败平台**；系统按 `retry_platforms` 只重跑这些平台，不会重跑已成功的平台
4. 每月 1 号跳过前一日比较；其他日期严格将当日累计值与自然日前一天比较，后一天更少即标记为需复核
5. 对「收入异常」逐条复核：它表示单日收入相对近期采集记录明显偏离

> `missing_platforms` 仍只表示完全没有入库数据的平台；`retry_platforms` 是实际补采集合，包含缺失平台以及最新任务失败/停止的平台。后续补采成功后，该平台会自动退出待补采集合。质量检查本身只读，只有管理员点击补采按钮才会创建采集任务。

> 门店覆盖优先按当月目标表核对；未配置目标表时按上一次采集日的门店列表核对。

日志记录按日期倒序分页展示，可与同页的数据健康结果一起定位问题。

### 3.9 货款核算

拥有 `admin.access` 的用户可在管理后台展开侧栏 **货款账册**，选择 **每日导入、累计汇总、月末核对、进场货款**：

1. 看板操作栏的 **导入货款**、侧栏 **货款账册 → 每日导入** 会直接打开每日导入页；日期默认为今天，也可以在日历中改选。
2. 选择包含“店名”和“金额”的 Excel 后点击 **导入选中日期**。同一天重复导入会覆盖该日期原始数据，页面会显示条数和合计。
3. **月末核对**选择月份后，只读取该月最后一个自然日导入的数据。例如 7 月只读取 `07-31`，不会使用 `07-30` 替代。
4. “缺少数据”不等于 0 元；只有原始文件明确包含该门店且金额为 0 才显示 0 元。
5. 未匹配原始店名会单独列出，其金额不会静默并入其他门店。先修正门店映射，再进行月末关账。
6. **进场货款**自动读取数据看板标准门店；默认显示在营门店，可切换全部、撤店/历史、已填写和未填写。修改会追加新版本，不覆盖旧修订。
7. **累计汇总**按门店计算“进场货款 + 已结束月份的月末基础货款 + 月末净积分 × 1.5”。积分直接读取每日采集数据中的当月累计增加和减少，不能把每日快照相加。
8. 基础货款和积分都只认最后一个自然日；缺少该日快照时会列出缺失月份，并把总额标记为“阶段小计”，不会把缺失记录当成 0。
9. 当前月尚未结束，不进入累计汇总。出货货款尚未接入时显示为空，也不参与已知总货款。
10. 展开 **月末快照覆盖情况**，可逐月检查基础货款、净积分及积分金额；积分换算固定为 **1 分 = 1.5 元**。

## 4. 常见问题

### 无法登录或页面提示无权限

- 确认账号尚未被管理员停用。
- 登录后只能访问已授权区域；需要下载或进入后台时，请联系用户管理员增加对应权限。
- 会话超过 12 小时、权限被调整或密码被重置后，需要重新登录。
- 同一来源地址与账号组合在 15 分钟内连续失败 5 次后，会暂停登录 15 分钟并返回 HTTP 429；其他来源不受影响。成功登录会清除该组合的失败记录。
- 所有页面和 API 都附带防嵌入、禁止 MIME 猜测、来源策略和内容安全策略等响应头；通过 HTTPS 访问时还会发送 HSTS。

### Cookie/密码过期
- 凭证管理页更新后点保存即可，下次采集自动使用新凭证
- **美团凭证过期**：编辑 `crawlers/meituan_download.py`，替换 MTGSIGS/COOKIES 列表中的值

### 抖音登录弹窗
- 抖音采集时会自动打开浏览器登录
- 如果弹出滑块验证码，需要人工拖动一下
- 登录成功后浏览器自动关闭

### 采集失败
- 查看数据看板「最近日志」中的错误信息
- 常见原因：网络超时（自动重试）、凭证过期、风控拦截
- 重试仍失败：检查凭证是否过期

### 自动采集没有运行或只有部分数据

- 服务必须持续运行；关闭终端或电脑会使排程停止，当日再启动时才会补跑。
- 查看管理后台的自动采集状态和采集日志；`partial` 表示至少一个平台成功，但未达到全部 13 个数据源。
- 八达通、货款等本地文件路径在运行机器上必须存在；平台凭证过期或验证码/风控也可能使自动批次成为 `partial` 或 `failed`。
- 点击自动采集卡的“查看并补采”，在采集日志的数据健康区域核对缺失或最新失败/停止平台；确认数源已就绪后，由管理员手动补采。
- 未配置告警 webhook 时不会向外部群聊主动通知，但失败事件仍保存在本地；系统不会自动重跑，不需要让门户查看用户获得采集权限。

### 健康检查与备份

- `GET /health/live`：只检查 Web 进程是否能响应，不访问数据库。
- `GET /health/ready`：检查 SQLite 可读、本进程持有单进程锁、Fernet 密钥有效，以及最近一份自动备份未超过 36 小时。任一关键项失败返回 HTTP 503。这两个地址无需登录，响应不包含文件路径或凭证。
- 服务对已有数据库执行初始化或结构迁移前，会先创建一次成对备份；运行期间每小时检查，确保每天至少一份有效备份。
- 自动备份位于 `data/backups/automatic/backup-*`。每个目录同时包含 `app.db`、`fernet.key` 和 `manifest.json`，三者必须作为一个整体异地复制和恢复。
- 默认保留 30 天。程序只清理带有效清单的自动备份目录，不删除人工备份或无法识别的目录。
- 恢复前应先停止服务，校验 `manifest.json` 中的 SHA-256，并用同一目录的 `fernet.key` 恢复 `credentials/.fernet_key`；数据库和密钥不可混用不同日期的版本。
- 主应用日志写入 `data/logs/app_fastapi.log`，单文件达到 10 MB 后自动轮转，最多保留 10 份历史文件；所有轮转文件继续执行敏感参数脱敏。
