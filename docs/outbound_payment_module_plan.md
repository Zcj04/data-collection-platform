# 出货货款采集模块规划

日期：2026-08-31。实施状态：第一、二步已落地，包括后台月度采集、完整版本保存、出货货款页面与门店/日期/商品/设备明细。第三步累计货款公式仍待业务确定，未修改。

操作与验证记录见 `docs/outbound_payments_usage.md`。下文保留规划依据和范围。

## 1. 试采依据与目标

已从多金宝“示例品牌”总部取回 2026 年 7 月 1—31 日全部设备库存流水：31/31 天、N条，涉及 10 家门店，均唯一匹配当前系统标准门店。设备出礼 N条、N件，平台原始成本合计 -N.57元，流出成本展示值 N.57元。

全量分页、日期范围、数量平衡、金额乘法均通过校验；逐日、逐店、整月金额一致。深H商圈存在 5 条零成本出礼；广州A商圈仅 4 天有出礼记录。接口还包括调入设备、设备调出、盘盈、盘亏、库存初始化、设备清零，不能全部作为出货。

本模块解决三个问题：按自然月逐个采集；按标准门店查看每月出货数量与成本；从汇总追溯到日期、商品、设备及来源流水。第一版不改变累计货款公式，不启用无人值守定时任务。

## 2. 页面位置与操作

在“货款账册”父级下面增加“出货货款”，保持现有每日导入、累计汇总、月末核对、进场货款及桌面/移动端导航习惯。

| 区域 | 展示与操作 |
| --- | --- |
| 月份与采集 | 选择月份，采集该月、重新采集；支持起止月份时按月份顺序排队，不能同时操作同一总部会话 |
| 任务进度 | 当前月份、当前日期/页码、已完成天数、记录数、失败原因；可停止、重试失败日期，刷新页面后进度仍在 |
| 月度概览 | 已完成天数/应采天数、有流水门店数、出礼数量、已记录出礼成本、待核对条数；独立显示“采集完整”和“成本待核对” |
| 门店明细 | 标准门店、原始店名、出礼条数/数量/成本、有出礼记录天数、零成本条数、映射与数据状态；按金额/数量排序，按门店筛选 |
| 门店展开 | 每日出礼变化、按商品/设备汇总；点击日期或商品进入源流水，支持日期和变更类型筛选、后端分页 |
| 库存调整 | 另一个明细视图展示全部变更类型，保留正负号；按金额绝对值排序辅助检查，不混入出礼成本 |
| 逐月查看 | 每个月一行：完整性、门店数、出礼量、已记录成本、更新时间、待核对数；可选门店查看各月数据 |

默认查看最近已采集的完整自然月。未采集的月份显示“未采集”；采集失败显示“未完成”，不显示 0 元。本次只有 7 月完整样本，不生成虚构的环比或走势；后续有连续完整月份时才展示环比，上一自然月缺失时明确提示，不跳月比较。

第一版只接受已结束月份。未来若需要当月预览，应明确显示“截至昨天，月份未结束”，不得混入完整月度累计。8 月数据最早 9 月 1 日才可标为完整自然月。

## 3. 计算与数据边界

- 默认“出货”展示仅取 `businessTypeDesc == 设备出礼`，这是建议展示口径；正式是否计入货款及与总货款的加减关系仍待业务确认。
- 出货数量 = `-Σ stockCount`；已记录出礼成本 = `-Σ sumCost`。使用原金额反向展示，不对每条金额取绝对值；若未来出现正向冲回，保留并标记，不擅自计入普通出礼。
- 保存平台原始符号；金额以 Decimal 校验，正式库存变更金额使用整数分保存，若超出两位小数先提示精度问题，不能静默四舍五入。`skuPredictCost` 保留平台返回的小数值，用于核对，不用它重新覆盖 `sumCost`。
- 平台字段名为“预估成本”；43.656057 万元是平台已记录成本，不宣称已核定应付货款。零成本 5 条保留为 0 并显示待核对，缺失金额则为未知，不能填 0、不能用其他记录价格补齐。
- 数据只代表该账号/总部可见的设备库存报表。本次账号组织列表有 12 家门店，报表中出现 10 家，不等于全公司其他门店的出货为零。
- 同时保留 `source_store_name` 和标准门店。使用现有 `company_organizational_structure.duojinbao` 映射，精确且唯一才匹配；未知名称、一个来源名称对应多家标准门店均保留原始数据并列为待匹配。
- 保留采集时的映射快照；后续调整映射不能无声地改变历史报表。历史月份不因门店当前已撤店而删掉流水。
- “全部日期接口读取成功”与“该门店每天有记录”是两件事。没有门店流水时显示“无源记录/适用期待核对”；白云月初无流水不能推定开业日，也不能认定是漏采。

## 4. 月份采集与重采

1. 后台接收月份和总部账号引用，校验管理员权限及 CSRF，创建月度批次；多个月份按时间顺序运行。
2. 用专用会话登录并精确选择 type=3 的“示例品牌”总部。凭证使用现有加密凭证管理，单独引用总部采集账号，不覆盖原有其他多金宝采集账号，不在日志里输出登录正文/Cookie。
3. 自然月拆为一天一天读取，每天从 pageIndex=1 开始、pageSize=200；日期范围为当天 00:00:00—23:59:59。这样避免假定整月接口请求没有时间跨度或条数限制。
4. 每天校验返回页码、总数、页数、日期、重复页；仅网络超时、429、服务暂时错误有限重试。认证失效或结构变化立即停止，不用空数据当成功。
5. 每天完整取回后，原子保存该批次当天的完整记录及分页证据；失败日期不写半页结果。继续任务时重试完整失败日，不从不可靠的半页位置拼接。
6. 只有 28/29/30/31 个应采日期全部成功、记录数和金额对账一致，才在事务内切换该月的可见版本。重采过程中继续展示旧的完整版本；失败、取消和进程重启都不能发布半个月结果。
7. 月度版本以“总部标识 + 月份”为范围，同范围一次只运行一个任务；日志记录批次、日期/页码、数量、校验问题，不记录个人信息。

这次响应没有独立流水主键。不能用商品 ID 去重，也不能把相同字段的两条合法记录合成一条。建议以“批次 + 日期 + 行序号”存源行，行哈希仅做差异诊断；重采按完整月份版本替换，不逐行追加到旧月份，避免重复计费。

## 5. 最小存储与代码边界

建议 3 张业务表，复用现有用户、权限、加密凭证和日志功能：

| 表（拟定名） | 主要职责 |
| --- | --- |
| outbound_collection_runs | 月度批次：总部标识、账号引用、月份、起止日、采集状态、核对状态、进度、操作者、时间、错误、是否当前版本；同总部同月最多一个当前完整版本 |
| outbound_collection_days | 批次每日状态：日期、源总数/页数、已读数、校验摘要、完成时间；唯一键为批次+日期 |
| outbound_stock_records | 批次源流水：日期、行序号、原始店名、标准门店及映射状态、设备/商品、变更类型、数量、原始成本、预估单价；按批次+门店+日期建查询索引 |

记录保留商品 ID、设备信息、变更时间和数量成本字段；第一版不落库操作人和自由文本备注。每日成功状态与明细写入同一事务；创建表和首次导入前备份 SQLite。

月度、门店、商品、每日汇总直接按当前完整批次查询，先不额外建预聚合表。当前样本 N条，页面明细必须后端分页，不能一次塞入浏览器；是否新增缓存以实际查询性能为依据。

代码建议：

- `crawlers/duojinbao_equipment_stock_crawler.py`：认证复用、总部选择、只读取数及分页校验；目前已支持单日和已结束月份的本地试采。
- `core/outbound_payments.py`（新增）：批次/每日/流水事务，类型计算，门店映射及查询。
- `core/outbound_collection.py`（新增）：后台顺序任务、进度、失败重试和取消；不要塞入现有按日平台收入汇总，避免混淆累计收入与库存流水。
- `app_fastapi.py`：管理员接口，加入现有 `ADMIN_API_ROUTES` 边界，保留统一的认证和 CSRF 中间件。
- `templates/dashboard.html` 和共享 CSS：增加货款子页、采集进度和门店下钻，不重构现有账册其他页签。

建议接口统一放在 `/api/payment-accounting/outbound/` 下：月份列表、月份概要、门店/商品/日期明细、流水分页；POST 启动采集、停止批次、重试失败日；GET 查询批次状态。具体返回结构跟随现有系统规范。

验证要覆盖自然月长短和闰年、时间边界、未结束月份拒绝、总数变化、重复页、缺页、金额缺失、零成本、未知变更类型、门店重名、重采版本切换、并发启动、取消后禁止发布、重启后的任务状态恢复。上线前重启本地服务，核对模板缓存版本，并在真实浏览器检查切页、进度、分页、筛选和移动端溢出。

本次已执行 7 项爬虫测试，并完整拉取真实7月数据、校验本地31个日文件；这不是上述整套后台模块的已完成验收。

## 7. 尚需业务确定的两项

1. 出货货款是否仅包含“设备出礼”，并直接采用平台的 `sumCost`（预估成本口径）；库存调拨和盘点仍应单列。
2. 在现有“进场货款 + 月末基础货款 + 净积分 × 1.5”的基础上，出货货款应如何计入总额。目前不推断加减，也不改变积分折算规则。

这两项不阻塞第一、二步的采集与展示，但必须在第三步正式入账前明确。
