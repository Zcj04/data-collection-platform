## 1. 项目背景与目标

### 1.1 现状

数据专员当前使用八爪鱼 RPA 配合 Python 爬虫脚本，从 5+ 个平台（美团商户后台等）获取门店经营数据。日常工作流程为：每日手动打开八爪鱼，逐个平台运行爬虫，等待抓取完成后，手工把各平台数据汇总到一张表格中，再提交给"数据小庄"。

### 1.2 痛点

- **重复操作**：每天逐平台手动运行爬虫，耗时且易遗漏
- **流程割裂**：各平台爬虫独立运行，数据分散，需人工汇总
- **效率低**：平台串行执行，无法并行，等待时间长
- **状态不可见**：爬取过程中无法直观看到进度，失败需手动排查
- **凭证维护麻烦**：Cookie、动态签名等凭证过期后需手动处理，无统一管理入口

### 1.3 项目目标

构建一个集成数据采集平台，**替代每日手动逐平台运行爬虫的工作流**，实现：
- 一个页面以表格形式汇总展示所有平台数据，支持按日期筛选
- 默认排程自动采集经营数据，管理员仍可按需手动全量、单平台或缺失补采
- 爬取（含报告下载与二次处理）完成后自动填入表格对应列
- 任务进度实时可见，失败可重试
- 财务、管理层等查看用户可登录数据门户自助取数，但不能触发采集或接触平台凭证

### 1.4 项目范围

**包含**：
- FastAPI 网页工作台（数据看板 / 数据大屏 / 每日经营数据 / 采集日志 / 凭证管理）
- 各平台爬虫的适配器集成（原脚本零改动）
- 多平台并行调度与任务状态管理
- 经营数据每日自动排程、持久化防重与错过时段补跑
- 自动采集异常的站内提示、质量检查与管理员手动补采闭环
- SQLite 数据存储与汇总
- 凭证加密存储与更新
- 内部用户登录、数据门户与管理后台权限分离

> 实现说明（2026-08-12）：原 Streamlit 版本已停用并从当前仓库移除，现仅维护网页工作台（`python app_fastapi.py` → `http://localhost:8010`）。

**不包含**：
- 多部门/多门店数据行级隔离（账号—门店绑定及主要看板、汇总、老板报表、监控和货款读取过滤已实现；新增接口仍需遵循同一范围校验）
- 爬虫脚本本身的重新开发（仅集成现有脚本）
- 美团官方开放平台 API 接入（见合规提示，由用户另行评估）
- 部署、HTTPS 反向代理和钉钉/企业微信等外部异常消息通知（属于上线阶段，本阶段未实现）

## 2. 干系人与角色

| 角色 | 说明 |
|---|---|
| 平台管理员（平台负责人） | 拥有全部模块权限，管理账号、凭证、采集任务和所有经营数据；可从管理后台进入数据门户 |
| 老板/财务 | 使用门户查看全量经营数据，下载汇总数据和每月货款比老板报表，查看数据监控及货款数据；不具备采集、凭证或用户管理写权限（对应 `portal.view`、`portal.download`、`boss_report.download`、`monitoring.view`、`payment.view`） |
| 货款数据管理员 | 每日上传、修订和维护货款数据，并可查看货款核算结果（对应 `payment.manage`，自动包含 `payment.view`） |
| 门店负责人 | 仅查看并下载所负责门店的数据；账号可绑定指定门店，登录后默认进入 `/store` 门店看板，主要读取接口已按绑定范围过滤 |
| 平台/爬虫 | 各平台爬虫脚本（美团等 5+ 个），由适配器统一调度 |

## 3. 术语表

| 术语 | 含义 |
|---|---|
| 适配器（Adapter） | 封装单个平台爬虫的统一接口层，对外暴露 `run(date)`，对内调用原脚本并标准化输出 |
| 汇总表 | 前端主表格，行=日期，列=各平台指标，集中展示所有平台数据 |
| 任务（Task） | 一次"某平台某日期"的采集执行单元，含状态机 |
| 自动采集批次 | 由一个经营数据排程时段触发的 13 平台采集；用 `scheduled_collection_runs.job_key` 持久化防重 |
| 凭证 | 爬虫运行所需的身份信息，如美团 Cookie、动态签名 mtgsig |
| mtgsig | 美团商户后台请求的动态签名参数，每次请求实时生成，不能写死 |
| 同步平台 | 输入日期后直接返回数据的平台（多数平台） |
| 异步平台 | 需"提交任务→轮询→下载报告→解析"多步骤的平台（仅美团） |

## 4. 功能需求

### F1 数据看板与日期筛选

**描述**：主页以大表格展示所有平台按日期汇总的数据，支持按日期筛选。

**详细要求**：
- 顶部日期选择器，可选定日期范围，表格展示该范围数据
- 支持日期范围一键采集（实现：操作栏日期范围 + 「全部采集」按钮）
- 表格行=日期，列=各平台指标 + 采集状态 + 操作
- 表格支持排序
- 默认展示最近 N 天数据，可翻页或滚动

**汇总表列结构**：见第 5.1 节。

### F2 触发采集

**描述**：经营数据默认按固定时段自动采集；拥有 `admin.access` 的管理员可按日期手动触发兜底采集。

**详细要求**：
- 时区固定为 `Asia/Shanghai`；每日 10:10 只采集目标月份 1 日至昨日的正式累计数据，不采集当天未结束数据
- 排程默认启用，时段与开关可在 `config.yaml` 的 `scheduler.auto_collect` 调整
- 经营数据排程与多金宝会员资产监控是两套独立任务，不共用时段、批次状态或结果表
- 服务在当日时段之后才启动时，自动补跑已错过且尚未成功领取的时段
- `scheduled_collection_runs.job_key` 在事务中防止服务重启或多进程同时检查时重复触发；终态为 `success` / `partial` / `failed` / `expired`
- 手动日期范围采集：管理员选定开始、结束日期后触发全部平台；自动排程的开始日期固定为截止日所在月的 1 日
- 单平台重跑与数据质量中心的缺失/失败平台补采用于失败兜底
- 只有 `portal.view` 的用户不得触发任何采集写操作
- 采集前自动校验凭证有效性，失效则提示前往凭证管理页更新
- 采集任务后台执行，不阻塞页面交互
- 同一日期 + 同一平台的重复采集，覆盖旧数据（UPSERT）

### F3 多平台并行调度

**描述**：5+ 平台爬虫并行执行，提升数据获取效率。

**详细要求**：
- 并行度 = 平台数（约 5），使用线程池
- 各平台独立运行，互不阻塞
- 单平台失败不影响其他平台
- 单平台总超时 10 分钟，超时标记失败
- 请求限流，避免触发反爬风控（每平台最小请求间隔 1-2 秒）

### F4 数据处理与汇总

**描述**：各平台爬虫返回数据后，经适配器标准化处理，汇总入库并展示。

**详细要求**：
- 适配器把原脚本的原始输出标准化为统一指标结构
- 美团特殊：原脚本下载 Excel 报告后，适配器做二次解析聚合（提取营业额、订单数等指标）
- 标准化数据 UPSERT 写入 `daily_summary` 表（按 date + platform 唯一）
- 前端表格从 `daily_summary` 读取并按列展示

### F5 任务监控与进度反馈

**描述**：实时展示所有采集任务的执行状态与进度（实现上已并入工作台「数据看板」区块）。

**详细要求**：
- 侧边栏平台状态列表实时展示每平台当前任务状态（状态圆点 + 标记）
- 状态：pending（待执行）/ running（执行中）/ success（成功）/ failed（失败）
- 美团异步任务显示分步进度（提交→轮询→下载→解析）
- 看板「最近日志」展示最近任务及错误信息
- 管理后台显示自动批次状态、13 源覆盖、真实入库时间和下次运行；门户仅显示不含敏感错误详情的相同新鲜度信息
- 最近自动批次为 `partial` / `failed` / `expired` 且尚未恢复时，管理后台显示站内待处理提示；管理员点击后进入该业务日期的数据质量中心
- 数据质量检查不能只看是否已有 `daily_summary`：平台已有旧数据、但该日期最新任务为 `failed` / `stopped` 时，必须标记为 `platform_failed`，提示当前展示的可能是旧数据
- 质量报告保留 `missing_platforms` 兼容字段，并提供去重后的 `retry_platforms`（缺失平台 + 最新失败/停止平台）；补采接口只在管理员点击后运行这些平台
- 同一平台后续最新任务变为 `success` 后，自动从 `retry_platforms` 和站内待处理提示中解除
- 前端每 8 秒局部刷新（仅看板页轮询，不重载整页）
- 历史任务日志表（最近 50 条）

> 本阶段的“异常闭环”仅指站内发现、定位和管理员手动补采；没有外部消息通知，也不会因出现异常而直接自动重跑。

### F6 凭证管理（账号密码中心）

**描述**：统一管理各平台爬虫所需的账号密码与凭证。用户明确要求：美团账号、芸苔账号等集中填写，运行时代码自动从这里获取，不写死在代码里。

**详细要求**：
- 凭证管理页按平台分组，每平台支持自定义凭证字段：
  - 美团：Cookie + mtgsig + partner_id（支持多组合伙人账号）
  - 芸苔：account（账号）+ password（密码）
  - 其余平台：按各自需求定义（账号密码 / Cookie / Token 等）
- 每平台表单：凭证字段输入框 + "测试连接" + "保存"按钮
- 凭证加密存储（cryptography Fernet），不明文落盘
- 适配器运行时从凭证管理读取并注入爬虫脚本（如芸苔 account/password 传给 main）
- 每日首次采集前自动健康检查，失效则弹窗提示更新
- 记录每凭证的最后更新时间、最近成功调用时间
- 美团 mtgsig 当前为硬编码（非动态生成，含时间戳易失效），阶段4 从脚本迁到凭证管理页统一更新
- 多账号支持：美团等多合伙人平台可配置多组账号；芸苔单账号多主体由脚本自动 LoginById 处理
- 实现（2026-08-12）：按平台折叠卡片，默认收起、点击展开（手风琴式，防误操作）；密码支持显示/隐藏；保存后状态徽章与统计实时更新；已保存凭证仅展示配置状态，不向浏览器回填密钥，留空保存保留原值

### F7 数据导出

**描述**：支持将汇总表数据导出为 Excel，便于提交给"数据小庄"。

**详细要求**：
- 导出按钮位于数据看板底部
- 导出当前筛选范围的数据（或选定日期范围）
- 格式为 .xlsx，列结构与汇总表一致

### F8 失败重试与熔断

**描述**：任务失败后支持重试，连续失败触发熔断保护。

**详细要求**：
- 网络/超时类异常自动重试，最多 3 次，指数退避（1s/2s/4s）
- 反爬类异常（403/风控）不重试，直接标记失败并提示更新凭证
- 单平台同日连续失败 3 次→自动熔断该平台，其余平台继续
- 汇总表"操作"列对失败任务提供"重试"按钮（单平台重跑）

### F9 历史数据管理

**描述**：保留历史采集数据，支持回溯查询。

**详细要求**：
- `daily_summary` 表保留所有历史数据
- 数据看板可按日期范围筛选查看历史
- 重复采集同日数据时覆盖（保留最新），不产生重复行

## 8. 约束与假设

### 8.1 约束
- 已有各平台 Python 爬虫脚本必须可直接集成，不重写
- 美团 mtgsig 为动态签名，依赖现有逆向成果，存在失效风险
- 单机本地部署，不引入 Celery/Redis 等分布式组件
- 自动排程依赖 Web 服务进程持续运行；生产初期限制为单 worker

### 8.2 假设
- 用户拥有各平台账号的合法访问权限，爬取的是自有店铺数据
- 各平台爬虫脚本以函数式返回 Python 对象（已确认）
- 仅美团为异步多步骤流程，其余平台均为同步流程（已确认）
- 网络环境稳定，可访问各平台商户后台

## 9. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| mtgsig 签名失效 | 高 | 独立存放 JS，便于替换；失败不重试超 3 次 |
| Cookie 过期 | 高 | 每日健康检查，失效提示更新 |
| 反爬风控 | 高 | 限流 + 退避 + 熔断 |
| 爬虫脚本崩溃 | 中 | 适配器 try/except 兜底，标记失败 |
| 自动采集部分成功 | 高 | 站内提示管理员进入质量中心；按 `retry_platforms` 手动补采缺失/失败平台，并检查凭证、验证码与本地文件路径 |
| 管理员未登录后台 | 高 | 当前无外部消息通知，站内提示无法主动触达；上线阶段需另行接入企业消息并配置服务健康监控 |
| 服务停止或多 worker 重复检查 | 高 | 服务持续运行、启动补跑，并用 `scheduled_collection_runs.job_key` 事务防重；生产初期单 worker |
| Excel 格式变更 | 中 | 按列名映射而非位置，容错解析 |
| 合规风险 | 中 | 见第 10 节，用户自行决策 |

## 10. 合规提示

美团《合规分管理规则》将"非法爬取""身份冒用""违规存储数据"等列为高风险扣分项。本平台技术上可行，但**实际使用需用户自行评估合规风险**。建议：
1. 优先评估美团官方开放平台（developer.meituan.com）申请 API 权限
2. 若使用现有爬虫方式，控制频率、仅采集自有店铺数据、不外传
3. mtgsig 维护依赖第三方逆向成果，存在被反制风险

本需求文档仅描述技术需求，合规决策由用户负责。
