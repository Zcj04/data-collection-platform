# 数据整合评估与实施方案

核查日期：2026-09-15。范围：现有主库、导入接口、项目报表、桌面货款/进场/盘点文件。桌面目录是临时存放位置，不代表完整历史。本次只读核查业务数据，未迁移主库或修改原表。

## 结论

现在有必要建立统一的数据管理和分析层，暂时没有证据需要另建大型数据仓库。建议继续使用现有 SQLite 主库，补齐进货明细、盘点、导入批次、门店映射，再提供按门店和月份查询的统一报表。不要把所有类型塞进一张表，也不要为每个月、每家门店新建表。

用户不需要维护固定目录。系统提供统一上传入口并自动保存原件，桌面文件只作为用户选择的导入来源。

## 已确认的整合难点

1. 当前货款上传接口只保存“货款店铺名、基础货款”，原文件里的商品和供应商明细没有进入主库。依据：app_fastapi.py 货款上传接口和 payment_imports 表结构。
2. 1—6 月货款表有前置“订购”列，7 月没有，列位置变化。必须按表头和区域识别，不能固定读取第几列。原表右侧还有店铺汇总区域，不能与左侧明细重复导入。
3. 进货存在“对账单价/单价”和“对账金额/金额”两套值，都应保留；核算用途需要明确，不能自动混用。
4. 发货日期可能是 Excel 日期序号，备注出现“已给厂家算上月货款”。核算月份和发货日期要分别保存，不能只按发货月份归账。
5. 盘点表结构不统一：部分是纵向明细，部分为多组横向布局。8 月汇总出现小数数量，需核查单位或表结构，不能强制取整或直接认定错误。
6. 商品名不具备稳定商品编码，门店名也有简称。第一阶段可完成门店月度分析，商品级跨来源自动对账要先建立映射，不能只凭相似名称自动合并。
7. 图片造成大文件：抽查东莞莞A商圈 8 月盘点文件总大小 161,070,644 字节，其中压缩图片约 161,001,209 字节。大文件不等于大量结构化数据。当前货款接口有 10 MB 上传限制，不能直接拿来接收这些盘点原件。

## 建议的数据组织

### 统一入口

上传 → 选择数据类型、核算月份、适用门店/区域 → 解析预览 → 展示匹配和异常 → 确认入库 → 查询/下载。

系统自动管理归档位置，例如 data/imports/<类型>/<年月>/<批次ID>/；这是建议路径，尚未创建归档或搬动桌面文件。大图片文件需要单独设计容量边界和后台解析；不能简单取消现有上传保护。

### 最小数据模型

| 组成 | 主要内容 |
| --- | --- |
| 门店主数据和别名 | 标准门店 ID、来源店名、开闭店期间，复用现有配置与生命周期 |
| 导入批次 | 类型、核算月、原文件位置、内容哈希、版本、状态、操作人、导入时间 |
| 进货明细 | 批次、源行、门店、商品原名/可选编码、数量/单位、供应商、两套价格金额、发货日、备注 |
| 盘点批次及明细 | 门店、盘点类型、核算月、实际盘点日（可待补）、商品、数量、价格金额、分类/上架状态 |
| 现有采集/进场/出库表 | 继续保留，不复制另一套权威数据；通过统一查询衔接 |
| 门店月度分析视图 | 收入、进货、进场、出礼成本、期初/期末盘点、数据截止日、完整性和待核对项 |

原始商品字段先保留，稳定商品 ID 在可靠匹配后补充。零和负数按业务类型保留；缺失值保留为空。金额保存精确值，单价保留必要小数精度，数量不能默认整数。币种不明时保留待确认，不能从门店所在地推定后直接汇总。

## 必须保持的口径

- 每日采集多为月累计：同月取所选截止日之前最后一份有效快照；月结复用现有严格月末规则。缺少月末不能伪装成已完成月结。
- 同一份货款的商品明细和门店汇总是两种粒度，只用于互相核对，不相加。
- 进场货款是否与某月进货重叠，需要来源核验；未确认前单独展示。
- 盘点是某个时点的存量，不能把连续月份库存金额累加为消耗。
- 在数量单位、成本口径、门店范围一致且调拨/退货/报损等齐全时，才可用“期初 + 进货 + 调入 - 调出 - 退货 - 期末”分析期间净减少。净减少还包含报损等因素，不能直接称为设备出礼成本或利润。
- 不把商品名相似当作同一商品，不把未匹配门店丢弃，不把未知日期补成月末。
- 保留原件、工作表和源行位置。重传同文件不重复计入；修正版替换有效版本并保留历史。同内容改文件名仍应识别。
- 新的查询、下载和导入继续执行服务端权限及门店范围限制。

## 实施顺序和验收

1. **先建立统一批次与进货明细导入。** 用 1—7 月不同布局验证识别，按门店逐月对照源表汇总及现有货款；差异列出，不直接覆盖现有金额。验证重复文件、更正版、负数、空值和事务回滚。
2. **接入月度盘点。** 先覆盖 7、8 月实际模板，纵向和横向表分别识别；核对门店/商品明细与汇总，缺少月份或日期明确提示。撤店和资产盘点独立分类。
3. **建立门店月度总览。** 连接已有采集、进场、进货、盘点、有效出库；每项显示来源和截止日。未补齐成本和调拨前只展示可核实项目及待核对差额。
4. **补商品和供应商映射。** 根据实际查询需要逐步完善，之后再做商品周转、供应商价格和精细耗用分析。

本次完成的是现状盘点及整合设计，尚未实施上述入口、表结构或历史迁移。正式迁移前备份现有库及配套密钥，运行样本核对；不主动重启服务。

## 什么时候再分库

若出现大量并发写入、复杂报表明显影响采集、多个应用共享数据库，再依据实测考虑服务器数据库或独立分析库。SQLite 官方适用场景与边界：https://www.sqlite.org/whentouse.html 。当前“表多、Excel 大”不足以单独成为迁移理由。
